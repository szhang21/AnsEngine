## GoalSummary

- 本轮目标：建立 `Engine.Runtime.Abstractions` 作为 runtime object/component 的共享抽象层，让未来自定义脚本程序集不需要引用 `Engine.Scene`。
- 成功标准：
  - `Engine.Runtime.Abstractions` 只依赖 `Engine.Contracts`。
  - `Engine.Scene` 实现 runtime object/component 抽象。
  - `Engine.Scripting` 消费 runtime abstraction，不依赖 `Engine.Scene`。
  - `MeshRenderer` 迁入 runtime component container。
  - `Transform` 继续作为对象空间核心字段保留独立访问。
  - 现有 Script/Physics/Render 主路径不退化。

## Scope

- In scope:
  - 新增 `Engine.Runtime.Abstractions` 模块与测试项目。
  - 定义 `IRuntimeComponent`、`IRuntimeObject`、`IRuntimeTransformComponent`。
  - `Engine.Scene` 实现 runtime abstraction contracts。
  - `SceneRuntimeObject` 新增 runtime component container 与 typed lookup。
  - `SceneMeshRendererComponent` 迁入 component container。
  - `Engine.Scripting` 对齐 runtime abstractions，同时保持 `context.Self.Transform` 兼容。
  - 新增并同步相关边界合同。
- Out of scope:
  - 自定义脚本程序集加载。
  - 脚本源码编译或热重载。
  - `IRuntimeUpdatableComponent` 或 `IComponent.Update()` 生命周期调度。
  - `RigidBody` / `BoxCollider` runtime component 化。
  - Animation component。
  - Editor authoring UI 新功能。
  - Play Mode。

## TechnicalDesign

### Dependency Direction

- `Engine.Runtime.Abstractions`:
  - allowed: `Engine.Contracts`, .NET standard library
  - forbidden: `Engine.Scene`, `Engine.Scripting`, `Engine.App`, `Engine.Render`, `Engine.Physics`, `Engine.SceneData`, `Engine.Editor`, `Engine.Editor.App`
- `Engine.Scene`:
  - may reference `Engine.Runtime.Abstractions`
  - continues to forbid `Engine.Scripting` and `Engine.Physics`
- `Engine.Scripting`:
  - may reference `Engine.Runtime.Abstractions`
  - continues to forbid `Engine.Scene`
- `Engine.Render` and `Engine.SceneData`:
  - must not reference `Engine.Runtime.Abstractions` in M22

Target graph:

```text
Engine.Contracts
        ^
Engine.Runtime.Abstractions
        ^                 ^
Engine.Scene        Engine.Scripting
        ^                 ^
        +------ Engine.App
```

### Public Abstractions

Add public contracts in `Engine.Runtime.Abstractions`:

```csharp
public interface IRuntimeComponent
{
}

public interface IRuntimeObject
{
    string ObjectId { get; }
    string ObjectName { get; }
    T? GetComponent<T>() where T : class, IRuntimeComponent;
    bool HasComponent<T>() where T : class, IRuntimeComponent;
}

public interface IRuntimeTransformComponent : IRuntimeComponent
{
    SceneTransform LocalTransform { get; }
    void SetLocalTransform(SceneTransform transform);
}
```

Do not add `Update`, `FindObject`, `AddComponent`, `RemoveComponent`, `Parent`, `Children`, `Scene`, or cross-object query APIs in M22.

### Engine.Scene Runtime Object Model

- `SceneRuntimeObject` implements `IRuntimeObject`.
- `SceneTransformComponent` implements `IRuntimeTransformComponent`.
- `SceneMeshRendererComponent` implements `IRuntimeComponent`.
- `SceneRuntimeObject` owns:
  - `SceneTransformComponent? Transform`
  - runtime component collection for non-core components
  - typed component lookup
- `Transform` remains an independent core spatial field in M22 and is not stored in the generic component collection, avoiding double ownership.
- `MeshRenderer` becomes the first generic runtime component and keeps a compatibility property:

```csharp
public SceneMeshRendererComponent? MeshRenderer =>
    GetComponent<SceneMeshRendererComponent>();
```

### Engine.Scripting Alignment

- `Engine.Scripting` references `Engine.Runtime.Abstractions`.
- `IScriptSelfObject` aligns with `IRuntimeObject` while preserving direct Transform access.
- Recommended shape:

```csharp
public interface IScriptSelfObject : IRuntimeObject
{
    IRuntimeTransformComponent Transform { get; }
}
```

- Current script update lifecycle stays in `ScriptRuntime`.
- Scripts still cannot query or mutate other objects.

### Runtime Data Flow

1. SceneData loads JSON into `SceneDescription`.
2. `Engine.Scene` builds `SceneRuntimeObject` instances.
3. Each runtime object stores core Transform and a generic component container.
4. Render path reads `Transform + MeshRenderer` and emits the same `SceneRenderItem` output as M21.
5. Scripting binds self object through App/Scene bridge and consumes runtime abstraction interfaces.
6. Physics writeback continues through `TrySetObjectTransform`.

M22 is a foundation milestone. It does not promise a new visible editor/runtime feature. Real main-path verification is still required through existing runtime behavior:

- Scene load produces the same render frame output.
- Script update still modifies self Transform.
- Physics writeback still resolves script-driven movement before render.
- Render and SceneData remain independent from runtime abstraction contracts.

## PlanningDecisions

- Do not define future-facing `IComponent` in `Engine.Scene`.
- Use `Engine.Runtime.Abstractions` as the shared abstraction module.
- Use `IRuntimeComponent`, `IRuntimeObject`, and `IRuntimeTransformComponent` naming to avoid confusing runtime components with SceneData/editor component DTOs.
- Keep Transform as core spatial field in M22.
- Migrate MeshRenderer first because it is a normal render capability component.
- Do not introduce updateable component lifecycle until M23+.

## Risks

- Risk: public abstraction API grows too much too early.
  - Mitigation: M22 forbids update, traversal, add/remove, and scene APIs.
- Risk: Transform becomes double-owned if also placed into component collection.
  - Mitigation: M22 keeps Transform as independent field only.
- Risk: Scripting alignment breaks current `context.Self.Transform` ergonomics.
  - Mitigation: preserve that property and adapt underneath.
- Risk: Render starts depending on runtime objects.
  - Mitigation: Render keeps consuming `SceneRenderFrame` only.

## Assumptions

- Future user scripts should reference `Engine.Scripting`, `Engine.Runtime.Abstractions`, and `Engine.Contracts`, not `Engine.Scene`.
- `Engine.Runtime.Abstractions` is the long-term shared runtime/script API seed.
- `Engine.Scene` remains the owner of concrete runtime object/component storage.
- `Engine.App` remains the composition root.
- M23 will decide whether Script binding enters component container and whether an updateable behavior contract is needed.
