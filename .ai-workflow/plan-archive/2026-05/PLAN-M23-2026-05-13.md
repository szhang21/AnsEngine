## GoalSummary

- 本轮目标：完成 Kinematic Physics State Synchronization，修正 M20 留下的 physics world state 与 Scene Transform 分叉问题。
- 成功标准：
  - `PhysicsWorld` 保留 non-mutating `ResolveKinematicMove(...)` 查询语义。
  - `PhysicsWorld` 新增 mutating kinematic move API，resolve 后更新 Dynamic body transform 与 AABB。
  - `RuntimePhysicsOrchestrator` 使用 mutating API，使 PhysicsWorld body state 与 Scene Transform 在每帧 resolve/writeback 后保持一致。
  - 连续多帧 kinematic movement 不再基于陈旧 physics body transform。
  - 现有 script -> physics -> scene writeback -> render 主路径不退化。
  - M23 不滑入 gravity、velocity、force、impulse、dynamic solver、dynamic-dynamic collision、trigger、CCD 或 Editor UI。

## Context

- M19 建立独立 `Engine.Physics` foundation，包括 `PhysicsWorldDefinition -> PhysicsWorld`、fixed step、snapshot、AABB/query。
- M20 完成 static collision + kinematic movement runtime MVP，由 App 在 script update 后调用 `PhysicsWorld.ResolveKinematicMove(...)` 并写回 Scene Transform。
- M20 明确把 `ResolveKinematicMove(...)` 设计为 non-mutating query：返回 resolved transform，但不更新 `PhysicsWorld` 内部 body snapshot。
- M21/M22 已关闭，M22 建立 runtime abstraction 与 component container；M23 不回改 M22 范围。
- 当前问题：dynamic body 成功移动后，Scene Transform 已更新，但 `PhysicsWorld` 内部 body transform/AABB 仍停留在 load-time 或上次未同步状态，后续连续帧 resolve 会基于陈旧 physics state。

## TechnicalDesign

### Dependency Direction

- `Engine.Physics`:
  - allowed: .NET standard library, `System.Numerics`
  - forbidden: any Engine module, OpenTK, ImGui, OpenGL
- `Engine.App`:
  - remains the composition root that owns Scene/Physics orchestration.
  - may reference `Engine.Physics` and `Engine.Scene`.
- `Engine.Scene`:
  - continues to expose transform writeback through existing runtime abstraction / scene runtime API.
  - must not reference `Engine.Physics`.
- `Engine.Render`, `Engine.SceneData`, `Engine.Scripting`:
  - no new dependency on `Engine.Physics`.

### Physics API Shape

Keep the existing API as pure query:

```csharp
public PhysicsKinematicMoveResult ResolveKinematicMove(
    string bodyId,
    PhysicsTransform desiredTransform);
```

Add a new mutating API:

```csharp
public PhysicsKinematicMoveResult ApplyKinematicMove(
    string bodyId,
    PhysicsTransform desiredTransform);
```

Required semantics:

- `ResolveKinematicMove(...)`:
  - validates input and body type as today.
  - returns desired/resolved transform and hit information.
  - does not mutate body transform or AABB.
- `ApplyKinematicMove(...)`:
  - validates input and body type with the same failure behavior as `ResolveKinematicMove(...)`.
  - computes the same resolved transform as `ResolveKinematicMove(...)`.
  - updates the target Dynamic body's stored `Transform`.
  - recalculates the target Dynamic body's `Aabb` from the updated transform and existing collider.
  - returns the same result shape.
- Static bodies cannot be moved by either API.
- Rotation remains excluded from AABB collision math, matching M20.

Implementation guidance:

- Extract the common validation + resolve calculation into a private helper to avoid rule drift.
- Because `PhysicsBodySnapshot` is currently an immutable record, mutation can be implemented by replacing the list entry with a new `PhysicsBodySnapshot`.
- Do not expose mutable body references.

### App Runtime Flow

Current flow remains:

```text
ProcessEvents
Input
Time
SceneRuntime.Update
ScriptRuntime.Update
Physics resolve/state-sync/writeback
RenderFrame
Present
```

M23 changes only the physics orchestration step:

```text
Scene snapshot desired transform
  -> PhysicsWorld.ApplyKinematicMove(bodyId, desiredTransform)
  -> PhysicsWorld updates body transform/AABB
  -> App writes resolved transform back to Scene
  -> Render observes Scene resolved transform
```

`Engine.Physics` still never writes Scene directly.

### Failure Semantics

- Missing body id, blank body id, non-finite desired transform, static body movement: same diagnostics as current resolve path.
- If `ApplyKinematicMove(...)` succeeds but Scene writeback fails, App returns failure before render, as today.
- M23 does not introduce rollback from PhysicsWorld if subsequent Scene writeback fails; QA must note this as current residual risk. If rollback becomes necessary, it should be a separate task because it requires transactional orchestration semantics.

## RuntimeRealityCheck

M23 changes a real runtime main path, not just tests or contracts.

Required real path:

```text
MoveOnInput or equivalent script updates Scene Transform
  -> App reads desired Scene Transform
  -> PhysicsWorld.ApplyKinematicMove resolves and updates physics body state
  -> App writes resolved transform back to Scene
  -> Render observes the resolved Scene Transform
  -> Next frame physics uses updated body transform
```

Unit tests are required, but M23 cannot be considered complete unless the App-level runtime path demonstrates consecutive-frame state sync.

## Risks

- Risk: Changing `ResolveKinematicMove(...)` directly would silently break query semantics.
  - Mitigation: keep it non-mutating and add `ApplyKinematicMove(...)`.
- Risk: Physics state mutates before Scene writeback, and writeback can fail.
  - Mitigation: preserve current fail-fast behavior and record non-transactional apply/writeback as residual risk.
- Risk: M23 expands into dynamic physics simulation.
  - Mitigation: explicitly forbid gravity, velocity, force, impulse, solver, trigger, CCD, friction and bounce.
- Risk: App tests overfit internals.
  - Mitigation: prefer observable snapshot/render behavior; use reflection only where existing tests already use it and no public seam exists.

## Assumptions

- M23 starts from closed M22 baseline.
- Static colliders remain the only blockers.
- Rotation remains ignored in AABB collision calculation.
- Dynamic body is still treated as kinematic when moved by script/logic.
- `PhysicsBodySnapshot` may remain immutable; world mutation can replace list entries.
- Transactional rollback between Physics apply and Scene writeback is deferred.
